# Desktop edition — M1: it runs without Docker

**Branch:** `desktop/m1` · **Status:** built, unsigned, Windows-verified · **PRD:** [PRD-desktop-edition.md](PRD-desktop-edition.md) §9

M1's contents per the PRD: bundled Postgres, PyInstaller engine, static SPA, tray
launcher, folder-watch intake. No AI, no modules, unsigned. Every item is below.

## Run it from a checkout

```bash
uv sync --extra dev --extra desktop --group build
uv run python scripts/desktop/fetch_postgres.py      # PostgreSQL 16.15 → vendor/postgres/
cd frontend && npm ci && npm run build:desktop && cd ..
uv run oh-desktop                                    # tray icon, opens your browser signed in
```

Useful flags:
- `--sample-data` loads the pilot's sample properties and drops the seven sample
  reports into the watch folder. It is for developers only.
- `--no-tray` runs in a console window.
- `--no-browser` prints the one-time sign-in address instead of opening it.

Set `OH_DATA_DIR=/some/scratch/dir` to keep a throwaway install away from your real one.

## Check it the way CI would

```bash
uv run python scripts/desktop/check.py          # everything
uv run python scripts/desktop/check.py --quick  # without the slow suites
```

Ruff, strict mypy, both test suites and the portal build, with one rule: a
check that could not run is reported as skipped and fails the run. See
[NEXT-STEPS.md](NEXT-STEPS.md) for why this is a command rather than only a
workflow.

## Build the app folder

```bash
uv run --extra desktop --group build python scripts/desktop/build.py
```

The output is `dist/Open Hospitality/`; run `Open Hospitality.exe` inside it. The
build is always one-folder, never one-file: pystray is LGPL-3.0 and must stay a
replaceable module (see `NOTICE`). M1 builds keep a console window so reviewers
can see the log. M3 removes it when signing arrives.

## What's in M1

| PRD M1 item | Where |
|---|---|
| Bundled Postgres | `src/usali/desktop/pg_runtime.py`: real PostgreSQL 16, so RLS stays a wall. Listens on 127.0.0.1 only, scram passwords, no Unix socket. Binaries come from `scripts/desktop/fetch_postgres.py`, checked against Maven's SHA-1 and a pinned SHA-256. |
| First-run database | `src/usali/desktop/bootstrap.py`: cluster roles, then migrations as the owner, then reference data, the founding org and the owner's grant. The USALI chart of accounts is re-seeded (insert-only) on every launch. Serving connects as `usali_app` only. |
| Engine binary | `packaging/desktop/open-hospitality.spec` (PyInstaller, one-folder). The bundle copies the repo layout, with the engine as source under `src/usali/`, so upstream's `Path(__file__).parents[2]` resource lookups (`gl_chart`, `qbo_push`, `preview`, `portal_api`) resolve without engine edits. |
| Static SPA | `npm run build:desktop` → `frontend/dist-desktop/`, served by the engine on 127.0.0.1 |
| Tray launcher | `src/usali/desktop/app.py`: menu items "Open my books", "Show my reports folder" and "Quit" |
| Folder-watch intake | `src/usali/desktop/intake.py`: watches "Drop reports here" and runs upstream's `process_file`, or `process_pack` for choiceADVANTAGE audit packs, unchanged |
| Sign-in (bridge to M2) | `src/usali/desktop/identity.py` and `session_api.py`: see [ADR-D1](adr/adr-d1-local-issuer.md) |

**The engine is not forked.** `create_app`, the verifier, tenancy, ingestion and
reporting are upstream's, used through the seams upstream's tests already use. The
upstream files that were modified are listed in `NOTICE`.

|---|---|---|

## Decisions, and where M1 departs from the PRD

1. **The live database is not in Documents** (PRD I-3). Documents is
   OneDrive-redirected on many Windows machines and iCloud-synced on many Macs. A
   sync client copying a running Postgres directory corrupts it. The owner's
   folder holds reports now and consistent backups from M3; the live files stay in
   app-data. ADR-D4 (backup and restore) should confirm this.
2. **Sign-in is a one-time launch code until M2.** The tray icon opens the browser
   with a two-minute, single-use code in the URL fragment. Every request must name
   a loopback Host, which blocks DNS rebinding. See ADR-D1.
3. **Keys live in `keys.json` until M2's keychain move** (done: see
   [ADR-D5](adr/adr-d5-keys-at-rest.md); an M1 install's `keys.json` is sealed and
   removed on its first M2 launch). That covers the database
   passwords, the field-encryption key, the HPKE key and the signing key. Lose the
   file and the books cannot be opened, so the M3 backup must carry it.
4. **Every connection starts Off** (PRD 5.3). On first run, upstream plants
   credential rows pointing at its local mock Gusto and QuickBooks; the bootstrap
   removes exactly those rows.
5. **Existing databases are not migrated silently** (PRD I-5). A newer build
   refuses to open older data until it is started with `--upgrade-database`. M3
   replaces the flag with a dialog and a pre-upgrade backup.
6. **Sample data is a developer flag, not a practice copy.** M2's first-run wizard
   builds the real practice copy as a separate database.
7. **Upstream's GL is required, not optional.** Since upstream's OH-27 cutover,
   the Summary Operating Statement reads the posted journal. Ingestion posts only
   when the org has a chart of accounts and the property has a fiscal calendar;
   otherwise facts land and the statement refuses. The desktop edition seeds the
   chart and tracks upstream's ledger rather than building its own (PRD open
   decision 6). Sample properties get a calendar-month fiscal calendar.

## Measured on Windows 10

| | |
|---|---|
| First run (initdb, all migrations, seed) to serving | ~17 s |
| Warm start to serving, including `uv run` | ~10 s. The PRD target is under 10 s, so this is borderline. |
| Crash recovery | Killed mid-run. The next start found the orphaned Postgres, stopped it and started clean. |
| Sample reports | 7 of 7 read, including the choiceADVANTAGE pack. Mapped counts match upstream's documented runs, with 0 unmapped. HISJ's statement for 2026-07-07 builds from the posted journal. |
| Sign-in | The one-time code was exchanged in a real browser, which landed on the dashboard as the owner. A spent or expired code is refused, and the refusal names the next step. |
| Tests | `tests/test_desktop_*` pass, 15 tests against the real bundled cluster with no Docker. `DesktopSignInPage.test.tsx` passes. |
| App folder build | 165–207 s. The folder is about 243 MB uncompressed; the PRD estimate was about 168 MB compressed. |
| Packaged app, first run | About 56 s from launch to serving: 13 s before the first log line, then 40 s creating the database. That is slower than the 17 s from a checkout, probably because Windows Defender scans freshly unpacked binaries (not confirmed). All 7 sample reports were read, the pack included, and the HISJ statement returned 200. |

## Known gaps

- **A real owner can't get a statement without two setup steps.** Their property
  must exist and have a fiscal calendar before the first report arrives. In M1
  only `--sample-data` creates properties; M2's first-run wizard has to ask for
  the property, its PMS and its fiscal calendar.
- **Adding a second person fails loudly.** Upstream onboarding calls the Keycloak
  admin client; M2 provides a local implementation of that seam.
- **macOS has not been built or run.** The darwin Postgres jars have no SHA-256
  pin yet; the fetch script refuses them until someone pins them on a Mac.
- ~~The tray icon has not been exercised here.~~ Exercised in the packaged
  Windows build on 11 September 2026: the app runs under the tray icon with no
  console fallback.
- **Upstream's full test suite was not re-run.** No engine code changed, but a
  weekly rebase should run it.
